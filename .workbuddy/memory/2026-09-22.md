## 16:20– 推送挂死排查：`GIT_CONFIG_NOSYSTEM=1`

**现象**：库布里克那轮提交后 `git push` **无输出挂死**（`git push -v` 停在 `Pushing to https://gitee.com/ZionZhang/zion-skills.git` 之后不动），`timeout 45` 报 `EXIT=124`，`git status -sb` 显示 `[ahead 1]`。

**排查路径（顺序值得记住）**：

1. **先排除网络**：`env | grep -i proxy` 确认沙箱确实注入了 `http(s)_proxy=http://127.0.0.1:49761`；`curl` 直连 gitee 返回 **HTTP=200 / 1.9 秒**——直连是通的，问题不在网络、也不在代理设置。
2. **再用 `GIT_TRACE=1` 定位**：trace 显示卡在 `git credential-helper-selector get`。它从 16:21:37 跑到 **16:22:15（约 38 秒）**，内部连做 `git config credential.helperselector.selected`、`git config --show-origin credential.helper`、`git config --system -e` 数次查询，**中间约 36 秒无任何动作**，之后才启动 GCM。我的 `timeout 40／45` 正好在它跑完前把进程杀了。

**根因**：PortableGit 的**系统级** `etc/gitconfig` 设了 `credential.helper=helper-selector` 这个 shim，每次认证固定开销约 40 秒。**这正是用户两轮前问的「为什么反复验证 credentialHelperSelector」的真正答案**——它确实每次都跑，内部就是一串 `git config` 查询；我上轮回答「它在后台过一下就完事、不会弹窗」低估了它（不弹窗是对的，开销和可见性判断错了）。

**解法**：**`GIT_CONFIG_NOSYSTEM=1`**（忽略系统级配置，**不改任何文件**）→ 直接走 global 的 GCM → **秒成**，`c206571..9742b2c` 一次通过。已写入 `MEMORY.md` 的 Git 节，并附「推送后确认用本地命令，别用 `git ls-remote`（它同样要走这条链）」。

**教训**：`timeout` 既是保护也是陷阱——第一次运行（90 秒）被杀时我只看到「没有输出」，差点误判成网络问题；**加上 `-v` 和 `GIT_TRACE=1` 才看清是凭据链**。以后 push 失败先看 trace，别先猜网络。
